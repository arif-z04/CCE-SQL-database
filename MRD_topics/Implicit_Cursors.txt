--------------------------------------------------------------------------------
1. TITLE & CONCEPTUAL DEFINITION
--------------------------------------------------------------------------------
In Oracle PL/SQL, an Implicit Cursor is a private memory work area automatically 
allocated, managed, and closed by the Oracle server whenever a SQL Data 
Manipulation Language (DML) statement (INSERT, UPDATE, DELETE, MERGE) or a 
single-row query (`SELECT ... INTO`) is executed inside a PL/SQL block without an 
explicit `CURSOR cursor_name IS` declaration.

Why it is used in Oracle Database:
- Zero Boilerplate: Eliminates programmatic `OPEN`, `FETCH`, and `CLOSE` commands.
- Compiler Optimization: Oracle PL/SQL Compiler (`PLSQL_OPTIMIZE_LEVEL >= 2`) 
  automatically rewrites single-row `SELECT INTO` statements into an optimized 
  2-row array fetch at the C-kernel level, making it faster than manual explicit 
  cursors for single-row lookups.
- Resource Safety: Memory is freed immediately upon completion of the SQL statement, 
  preventing session resource exhaustion (`ORA-01000: maximum open cursors exceeded`).
- Rich Execution Telemetry: Oracle provides immediate execution metrics via the 
  `SQL%` cursor attribute pseudo-object (`SQL%FOUND`, `SQL%NOTFOUND`, `SQL%ROWCOUNT`, 
  `SQL%ISOPEN`, `SQL%BULK_ROWCOUNT`, `SQL%BULK_EXCEPTIONS`).

Problems it solves:
- Eliminates unclosed cursor leaks in long-running Oracle sessions and connection pools.
- Enforces strict single-row uniqueness assertions in transactional logic (raising 
  predefined Oracle exceptions `NO_DATA_FOUND` / `TOO_MANY_ROWS` if violated).


--------------------------------------------------------------------------------
2. ARCHITECTURE & INTERNAL EXECUTION
--------------------------------------------------------------------------------

A. Oracle Memory Areas: PGA vs. SGA:
When an implicit cursor statement executes, the Oracle engine allocates and binds 
resources across two core memory structures:

  1. Shared Global Area (SGA - Shared Pool / Library Cache):
     - Oracle checks the Library Cache for a matching SQL ID (using SQL hash value).
     - If matched (`CURSOR_SHARING = EXACT` or bind-aware `FORCE`), a Soft Parse 
       re-uses the existing execution plan.
     - If not matched, Oracle executes a Hard Parse, optimizing and compiling 
       the statement into a shared cursor.
  2. Program Global Area (PGA - Private SQL Area):
     - Allocated in the session's UGA/PGA.
     - Holds bind variable values, persistent work area state, and execution buffers.
     - When the statement terminates, the PGA cursor handle is instantly marked 
       reusable or closed.

B. The PL/SQL to SQL Context Switch:
Execution transitions across the engine boundary:
      PL/SQL Engine  ----(SQL Command & Binds)---->  SQL Execution Engine
      PL/SQL Engine  <---(Data & SQL% Attributes)---  SQL Execution Engine

C. The Oracle 2-Row Fetch Rule for SELECT INTO:
To verify that a `SELECT ... INTO` query satisfies the relational uniqueness contract:
  - Fetch #1: Oracle fetches the first candidate row into target variables.
  - Fetch #2: Oracle immediately attempts to fetch a second row.
    * 0 rows returned: Oracle immediately raises `ORA-01403: no data found`.
    * 1 row returned: Query succeeds cleanly.
    * 2 rows returned: Oracle halts execution and raises `ORA-01422: exact fetch returns more than requested number of rows`.

D. Lifecycle of SQL% Attributes:
  - In Oracle PL/SQL, `SQL%ISOPEN` is ALWAYS evaluated to `FALSE`. Oracle closes 
    the implicit cursor before returning control to the next PL/SQL line.
  - `SQL%FOUND`, `SQL%NOTFOUND`, and `SQL%ROWCOUNT` reflect ONLY the most 
    recently executed SQL statement within the active block.

3. BASIC TO INTERMEDIATE IMPLEMENTATION
--------------------------------------------------------------------------------

-- =============================================================================
-- Setup Oracle Schema Objects
-- =============================================================================
BEGIN
    EXECUTE IMMEDIATE 'DROP TABLE bank_accounts CASCADE CONSTRAINTS';
EXCEPTION
    WHEN OTHERS THEN IF SQLCODE != -942 THEN RAISE; END IF;
END;
/

CREATE TABLE bank_accounts (
    account_id   NUMBER(10) GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    iban         VARCHAR2(34) NOT NULL UNIQUE,
    holder_name  VARCHAR2(100) NOT NULL,
    balance      NUMBER(14, 2) NOT NULL CHECK (balance >= 0),
    status       VARCHAR2(20) DEFAULT 'ACTIVE' 
                 CONSTRAINT ck_acc_status CHECK (status IN ('ACTIVE', 'FROZEN', 'DORMANT'))
);

INSERT INTO bank_accounts (iban, holder_name, balance, status)
VALUES ('GB29XABC10101012345678', 'Alexander Vance', 15450.50, 'ACTIVE');

INSERT INTO bank_accounts (iban, holder_name, balance, status)
VALUES ('GB29XABC20202087654321', 'Beatrice Sterling', 820.00, 'ACTIVE');

INSERT INTO bank_accounts (iban, holder_name, balance, status)
VALUES ('GB29XABC30303011223344', 'Charles Montgomery', 0.00, 'FROZEN');
COMMIT;

-- =============================================================================
-- Example 1: SELECT INTO with Native Oracle Exception Handling
-- =============================================================================
SET SERVEROUTPUT ON SIZE UNLIMITED;

DECLARE
    v_iban        bank_accounts.iban%TYPE := 'GB29XABC10101012345678';
    v_holder      bank_accounts.holder_name%TYPE;
    v_balance     bank_accounts.balance%TYPE;
BEGIN
    -- Implicit Cursor: Auto-allocated, executed, validated, and closed
    SELECT holder_name, balance
      INTO v_holder, v_balance
      FROM bank_accounts
     WHERE iban = v_iban;

    DBMS_OUTPUT.PUT_LINE('Holder : ' || v_holder);
    DBMS_OUTPUT.PUT_LINE('Balance: ' || TO_CHAR(v_balance, 'FML999,999,990.00'));

EXCEPTION
    WHEN NO_DATA_FOUND THEN
        DBMS_OUTPUT.PUT_LINE('ORA-01403: No account found matching IBAN: ' || v_iban);
    WHEN TOO_MANY_ROWS THEN
        DBMS_OUTPUT.PUT_LINE('ORA-01422: Critical data integrity error: Duplicate IBAN detected.');
    WHEN OTHERS THEN
        DBMS_OUTPUT.PUT_LINE('Oracle Error [' || SQLCODE || ']: ' || SQLERRM);
        RAISE;
END;
/

-- Sample Output:
-- Holder : Alexander Vance
-- Balance: $15,450.50

-- =============================================================================
-- Example 2: DML Inspection via SQL%FOUND, SQL%NOTFOUND, and SQL%ROWCOUNT
-- =============================================================================
DECLARE
    v_target_iban VARCHAR2(34) := 'NON_EXISTENT_IBAN';
    v_fee         NUMBER(6, 2) := 25.00;
BEGIN
    UPDATE bank_accounts
       SET balance = balance - v_fee
     WHERE iban = v_target_iban
       AND status = 'ACTIVE';

    IF SQL%FOUND THEN
        DBMS_OUTPUT.PUT_LINE('Success: ' || SQL%ROWCOUNT || ' account updated.');
    ELSIF SQL%NOTFOUND THEN
        DBMS_OUTPUT.PUT_LINE('SQL%NOTFOUND evaluated TRUE: Zero rows affected.');
    END IF;

    -- SQL%ISOPEN check in Oracle PL/SQL
    IF NOT SQL%ISOPEN THEN
        DBMS_OUTPUT.PUT_LINE('Confirmed: Implicit cursor is already closed by Oracle kernel.');
    END IF;
END;
/

4. ADVANCED REAL-WORLD USE CASES
--------------------------------------------------------------------------------

-- =============================================================================
-- Use Case 1: High-Throughput FORALL Bulk Processing with SAVE EXCEPTIONS
-- =============================================================================
-- Demonstrates FORALL with SQL%BULK_ROWCOUNT(i) and handling partial failures
-- using the Oracle error array SQL%BULK_EXCEPTIONS without statement rollback.

DECLARE
    TYPE t_iban_list IS TABLE OF bank_accounts.iban%TYPE;
    TYPE t_deduct_list IS TABLE OF NUMBER;

    v_ibans   t_iban_list   := t_iban_list(
        'GB29XABC10101012345678', -- Valid, Active
        'GB29XABC20202087654321', -- Valid, but deducting 1000 will violate balance >= 0 CHECK!
        'GB29XABC30303011223344', -- Valid, but status is FROZEN
        'INVALID_IBAN_999999999'  -- Non-existent
    );
    v_deducts t_deduct_list := t_deduct_list(50.00, 1000.00, 10.00, 20.00);

    v_bulk_error_count NUMBER;
    v_err_idx          NUMBER;
    v_err_code         NUMBER;
BEGIN
    BEGIN
        -- Execute batch update in a single engine context switch
        FORALL i IN v_ibans.FIRST .. v_ibans.LAST SAVE EXCEPTIONS
            UPDATE bank_accounts
               SET balance = balance - v_deducts(i)
             WHERE iban = v_ibans(i)
               AND status = 'ACTIVE';

    EXCEPTION
        WHEN OTHERS THEN
            IF SQLCODE = -24381 THEN -- ORA-24381: error(s) in array DML
                v_bulk_error_count := SQL%BULK_EXCEPTIONS.COUNT;
                DBMS_OUTPUT.PUT_LINE('>>> Encountered ' || v_bulk_error_count || ' exceptions during bulk DML:');

                FOR j IN 1 .. v_bulk_error_count LOOP
                    v_err_idx  := SQL%BULK_EXCEPTIONS(j).ERROR_INDEX;
                    v_err_code := SQL%BULK_EXCEPTIONS(j).ERROR_CODE;
                    DBMS_OUTPUT.PUT_LINE(
                        '    Item Index [' || v_err_idx || '] IBAN ' || v_ibans(v_err_idx) ||
                        ' failed with ORA-' || LPAD(v_err_code, 5, '0')
                    );
                END LOOP;
            ELSE
                RAISE;
            END IF;
    END;

    DBMS_OUTPUT.PUT_LINE('--- Batch Row Counts per Element ---');
    FOR i IN v_ibans.FIRST .. v_ibans.LAST LOOP
        DBMS_OUTPUT.PUT_LINE('Index [' || i || '] Rows Updated: ' || SQL%BULK_ROWCOUNT(i));
    END LOOP;
    DBMS_OUTPUT.PUT_LINE('Total Aggregate Rows Affected: ' || SQL%ROWCOUNT);

    ROLLBACK; -- Clean up test mutations
END;
/

-- Sample Output:
-- >>> Encountered 1 exceptions during bulk DML:
--     Item Index [2] IBAN GB29XABC20202087654321 failed with ORA-02290
-- --- Batch Row Counts per Element ---
-- Index [1] Rows Updated: 1
-- Index [2] Rows Updated: 0
-- Index [3] Rows Updated: 0
-- Index [4] Rows Updated: 0
-- Total Aggregate Rows Affected: 1

-- =============================================================================
-- Use Case 2: Atomic Conditional Merge/Upsert with RETURNING ... BULK COLLECT INTO
-- =============================================================================
DECLARE
    TYPE t_num_list IS TABLE OF NUMBER;
    v_modified_balances t_num_list;
BEGIN
    UPDATE bank_accounts
       SET balance = balance * 1.05
     WHERE status = 'ACTIVE'
 RETURNING balance BULK COLLECT INTO v_modified_balances;

    DBMS_OUTPUT.PUT_LINE('Records updated: ' || SQL%ROWCOUNT);
    FOR i IN 1 .. v_modified_balances.COUNT LOOP
        DBMS_OUTPUT.PUT_LINE('New Balance #' || i || ': ' || TO_CHAR(v_modified_balances(i), 'FM999,990.00'));
    END LOOP;
    ROLLBACK;
END;
/

5. USEFUL TRICKS & PERFORMANCE OPTIMIZATION
--------------------------------------------------------------------------------
1. PLSQL_OPTIMIZE_LEVEL & Automatic Array Fetching:
   - Always compile packages with `PLSQL_OPTIMIZE_LEVEL = 2` (default) or `3`.
   - At level 2+, Oracle automatically compiles `SELECT INTO` with an optimized 
     internal array-fetch of size 2. Do NOT convert single-row `SELECT INTO` queries 
     into explicit `OPEN-FETCH-CLOSE` cursors in an attempt to optimize; explicit 
     cursors will be slower due to additional roundtrip call overhead.

2. Aggregate Function Gotcha (COUNT, MAX, MIN, SUM):
   - A `SELECT INTO` query containing a SQL aggregate function (e.g. `MAX()`, `SUM()`) 
     NEVER raises `NO_DATA_FOUND` in Oracle if the `WHERE` clause matches 0 rows. 
     Instead, it assigns `NULL` (or `0` for `COUNT(*)`) to target variables.
   - Example:
       SELECT MAX(balance) INTO v_max FROM bank_accounts WHERE 1 = 2;
     Result: `v_max` is NULL; `NO_DATA_FOUND` is NEVER raised!
   - Best Practice: Explicitly test `IF v_max IS NULL THEN ...`.

3. Cursor Invalidation & Intermediate SQL Danger:
   - `SQL%` attributes are overwritten on EVERY SQL execution.
   - Anti-Pattern:
       UPDATE bank_accounts SET balance = balance + 10 WHERE account_id = 1;
       INSERT INTO audit_log VALUES (SYSDATE, 'UPDATED');
       IF SQL%ROWCOUNT = 1 THEN ... -- BUG: Evaluates the INSERT, NOT the UPDATE!
   - Best Practice: Immediately save the attribute into a local variable:
       v_rows_updated := SQL%ROWCOUNT;

6. QUICK REFERENCE / SYNTAX CHEAT SHEET
--------------------------------------------------------------------------------
+---------------------------+--------------------------------------------------+
| Oracle SQL% Attribute     | Data Type & Return Description                   |
+---------------------------+--------------------------------------------------+
| SQL%FOUND                 | BOOLEAN: TRUE if recent DML/SELECT affected >= 1 |
|                           | row; FALSE if 0 rows. NULL before any SQL runs.  |
| SQL%NOTFOUND              | BOOLEAN: TRUE if recent DML/SELECT affected 0    |
|                           | rows; FALSE if >= 1 row. Opposite of SQL%FOUND.  |
| SQL%ROWCOUNT              | NUMBER: Total rows affected or fetched by recent |
|                           | statement. In FORALL, returns total batch sum.   |
| SQL%ISOPEN                | BOOLEAN: Always FALSE in PL/SQL.                 |
| SQL%BULK_ROWCOUNT(i)      | NUMBER: Rows affected by the i-th statement in   |
|                           | a FORALL bulk execution construct.               |
| SQL%BULK_EXCEPTIONS.COUNT | NUMBER: Count of exceptions captured when FORALL |
|                           | runs with the SAVE EXCEPTIONS clause.            |
| SQL%BULK_EXCEPTIONS(j)    | Composite: .ERROR_INDEX and .ERROR_CODE (Oracle  |
|                           | error number without the negative sign).         |
+---------------------------+--------------------------------------------------+

Core Oracle Syntax:
-------------------
-- Single-row query:
SELECT col1, col2 INTO var1, var2 FROM tbl WHERE pk_col = bind_val;

-- Bulk DML with exception resilience:
FORALL i IN coll.FIRST .. coll.LAST SAVE EXCEPTIONS
    UPDATE tbl SET col = coll(i).val WHERE id = coll(i).id;

-- DML returning into collection:
DELETE FROM tbl WHERE status = 'PURGE' RETURNING id BULK COLLECT INTO id_list;
